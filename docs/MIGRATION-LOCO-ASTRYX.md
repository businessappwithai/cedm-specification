## 1. Executive summary

AppWithAI is a code generator. Its product is not an app — it is `packages/generator/templates/tanstack-start-nestjs/`, a 328-file, ~46 000-line Handlebars template set that emits a full-stack application from an ERD. Migrating "the backend to Loco.rs and the frontend to Astryx" therefore means **rewriting the emitted stack, plus the generator code that drives it**, not refactoring a running service.

The work splits into two largely independent tracks joined by a stable HTTP contract:

| Track | Nature | Size |
|---|---|---|
| **Backend → Loco.rs** | Language port (TypeScript → Rust) + framework port (NestJS → Loco/Axum) + ORM port (Kysely → SeaORM/sqlx/sea-query) | 162 template files, ~19 800 lines, 11 NestJS modules |
| **Frontend → Astryx** | Component-library and styling swap inside the *same* app framework | 166 template files, ~26 900 lines, 2 319 `className` sites, 14 Radix packages |

The backend track is the hard one, and the hardest thing in it is not syntax. It is that **the generated backend is metadata-driven at runtime**: one `BusController`/`BusService` pair serves every business table, resolving columns, validation, and form layout from the `sys_*` Application Dictionary on each request (`bus.controller.ts.hbs:38` — `@Controller('bus')`, routes are `/:entity/:id`). That pattern is trivial in TypeScript with `Kysely<any>` and is the single biggest design problem in Rust, whose ORM is compile-time typed. Section 6.3 proposes a concrete answer (sea-query dynamic builder over the sqlx pool that SeaORM already owns) and it should be prototyped before anything else is committed to.

The frontend track is mostly mechanical, and Astryx makes it more mechanical than expected: it ships pre-built CSS (no StyleX build plugin required) and a `tailwind-theme.css` bridge that maps its design tokens onto Tailwind utility names. That bridge allows an **incremental** migration — swap components first while 2 319 existing Tailwind classes keep rendering against Astryx tokens, then delete Tailwind — instead of a stop-the-world rewrite.

Recommended sequencing: **frontend first**. It is lower-risk, it validates the new stack ID and generator plumbing end to end, and it can ship against the existing NestJS backend because the HTTP contract does not change. The Rust backend then lands behind the same contract.

Total realistic effort, one experienced engineer: **frontend 3–5 weeks, backend 10–16 weeks** (§10). All eleven architectural decisions are **settled** (§12) — auth is Loco native JWT, hooks become generated Rust, Trigger.dev and immudb are dropped — so the remaining variance is Rust ramp-up and the volume of the `sys` dictionary module, not unresolved design.

## 2. Three findings that shape the whole plan

### 2.1 Astryx is a design system, not an application framework

The request says "frontend to astryx framework from meta." Astryx (open-sourced by Meta, June 2026, MIT, `github.com/facebook/astryx`) is a **React component library and theming system** — 124 exported component entry points, ten themes, a CLI, and an MCP server. Its own README is explicit: it "does not include routing or data fetching."

Concretely, `@astryxdesign/core@0.2.0` declares:

```json
"peerDependencies": {
  "react": ">=19.0.0",
  "react-dom": ">=19.0.0",
  "@stylexjs/stylex": "^0.19.0"
}
```

So the plan reads the request as: **Astryx replaces the presentation layer** — shadcn-style `components/ui/*`, Radix primitives, Tailwind utility styling, `class-variance-authority`, `tailwind-merge`, `lucide-react`. **TanStack Start / Router / Query / Table / Form stay**, because Astryx does not replace them and nothing else in the request suggests changing the app shell. Every generated route file, loader, and query hook keeps its structure.

If the intent was actually to also replace the app framework, say so and §7 needs rework — but there is no Meta framework that would fill that role here, and Astryx explicitly declines to.

One consequence is unavoidable and non-negotiable: **React 18 → 19**. The generated frontend currently pins `react: ^18.2.0` (`frontend/package.json.hbs:22`). Astryx requires ≥19.

### 2.2 The rules engine is already Rust — this migration makes it native

The generated backend evaluates GoRules JDM decision graphs via `@gorules/zen-engine@^0.54.0`, which is a **Node binding around a Rust core**. The same engine is published as the `zen-engine` crate (stable `0.55.1`, same version line). So:

- JDM files (`src/modules/rules/jdm/*.jdm.json`) port **byte-for-byte**, no semantic change.
- The `rules` → flowchart → JDM converter in `packages/web/src/lib/jdm-converter.ts` is untouched.
- The rules module stops paying an N-API boundary cost per evaluation.

This is the one module where the migration is a strict improvement with near-zero risk. It should be the first Rust module built, as a confidence-builder.

### 2.3 Loco.rs hit 1.0 — the target is stable

`loco-rs` is at **1.0.1** (crates.io, updated 2026-07-31), on `axum 0.8`, `sea-orm 2.0`, `sqlx 0.9`, `validator 0.20`, `jsonwebtoken 10.3`. The 1.0 architecture maps unusually cleanly onto what the generator already emits:

| Generated NestJS concept | Loco 1.0 equivalent |
|---|---|
| `AppModule` imports | `Hooks::routes()` in `src/app.rs` |
| Nest DI container | `AppContext` (cloned into every handler/worker/task) + `shared_store` for custom services |
| `@Controller('bus')` | `Routes::new().prefix("bus")` in `src/controllers/bus.rs` |
| Global pipes/filters/interceptors | `Hooks::middlewares()` + the LIFO middleware onion |
| `ThrottlerGuard`, CORS, ETag | Built-in configurable middleware (`config/*.yaml`) |
| Trigger.dev tasks | `BackgroundWorker` trait + queue provider (Postgres/Redis/tokio) |
| Custom Kysely migration runner (`src/migrate.ts`, 173 lines) | `migration/` crate + `cargo loco db migrate` |
| `bun test` HTTP suites | `tests/requests/` with `loco_rs::testing` |

`StartMode` also gives something the current design lacks: the HTTP tier and the job worker can be separate processes (`cargo loco start --server-and-worker` vs `--worker`), which is a real operational gain over the in-process Trigger.dev dispatcher.

## 3. Scope, goals, non-goals

### 3.1 Goals

1. Introduce a **new generated stack**, `tanstack-astryx-loco`, alongside — not replacing — `tanstackjs-nestjs`, until the new one reaches parity.
2. Preserve the **ERD → app contract**: the same model input must produce an application with the same behaviour, same REST surface, same Application Dictionary semantics, same business-rule and workflow outcomes.
3. Preserve the **runtime metadata architecture**: `sys_*` dictionary drives UI layout and validation; `bus_*` tables are served generically; `seq_no` still reorders fields without a redeploy.
4. Keep the generated app **runnable offline from bundled templates** (`skipCliScaffold` mode), as today.
5. Keep the **E2E suite green** — the `bun:test` HTTP suites under `<output>/tests` are stack-agnostic by design and become the primary parity oracle.

### 3.2 Non-goals

- Migrating the **AppWithAI host application** (`packages/web`, `packages/core`, `packages/ai`) to Rust or Astryx. It stays TanStack Start + Bun + Kysely. Only its *stack-selection* surfaces change.
- Changing **EML** (`language/appwithai-language.json`) semantics. Only `generatorContract.pipeline` prose gains a second target.
- Changing the **database schema**. Postgres stays; `sys_*`/`bus_*` DDL is identical, so an existing generated database can be served by either backend.
- Porting the **generator CLI itself** to Rust + clap. The generator's output being Rust does not require the generator to be Rust. *(Deferred — §12, D11; scoped in §8.7(e).)*
- Deleting the NestJS stack in this effort. It is **deprecated once parity is demonstrated**, with the date set at Phase 5 *(§12, D7)* — not removed as part of this work.

### 3.3 Definition of done

- `bun run generate:tanstack --stack tanstack-astryx-loco` produces a project that builds (`cargo build --release`, `bun run build`), migrates, seeds, and starts.
- The generated `tests/` suite passes against the Rust backend with **zero suite-level modifications** (harness config may change base URL only).
- A Playwright pass over the generated frontend matches the current screenshot inventory for the admin dictionary flows.
- `docs/`, `CLAUDE.md`, and `packages/generator/SKILL.md` describe both stacks accurately.

**Key architectural decisions, stated up front:**

1. **`sys_*` and auth tables get real SeaORM entities.** Their shape is fixed by the dictionary design, known at generation time, and they carry the most business logic. Compile-time typing is affordable and worth it.
2. **`bus_*` tables are accessed dynamically.** Their shape comes from the user's ERD. Even though the generator *could* emit SeaORM entities for them, the runtime contract (`sys_field.seq_no` reordering, dictionary-driven validation, `/bus/{entity}` accepting any entity string) is inherently dynamic. §6.3 details the mechanism. **Optionally** the generator also emits typed entities for `bus_*` for use in hooks and workflows — a nice-to-have, not a dependency.
3. **`AppContext.shared_store` is the DI container** for the four long-lived services (rules engine, dictionary cache, workflow executor, hook registry), initialized once in `Hooks::after_context`.
4. **The middleware onion replaces interceptors/filters/guards** — ETag, CORS, rate limiting, and request-ID come from Loco config; audit and `If-Match` handling are custom `tower::Layer`s.

## 6. Backend migration design — NestJS → Loco.rs

### 6.1 Framework primitive mapping

| NestJS primitive | Loco 1.0 | Notes |
|---|---|---|
| `@Module({imports})` | `Hooks::routes()` + `AppRoutes::add_route()` | Flat registration; no module graph |
| `@Injectable()` + constructor DI | `AppContext` param + `shared_store` lookups | No DI container; explicit is fine at this scale |
| `@Controller('bus')` | `Routes::new().prefix("bus")` | |
| `@Get(':entity/:id')` | `.add("/{entity}/{id}", get(handler))` | Axum 0.8 brace syntax, **not** `:id` |
| `@Body() dto` | `Json(payload): Json<T>` | |
| `@Query() q` | `Query(params): Query<HashMap<String,String>>` | |
| `@Headers('if-match')` | `headers: HeaderMap` or a typed extractor | |
| `@UseGuards(SessionAuthGuard)` | `auth::JWT` / `auth::JWTWithUser<users::Model>` extractor | Per-handler, compile-checked |
| `@UseInterceptors(AuditInterceptor)` | custom `tower::Layer` via `Routes::layer()` | |
| `APP_FILTER` (`HttpExceptionFilter`) | `impl IntoResponse for AppError` | §6.11 |
| `APP_INTERCEPTOR` (`TransformInterceptor`) | response shaping in `format::json` wrappers | §6.11 |
| `ThrottlerModule` | `middlewares.limit_payload` + rate-limit layer in config | |
| `ConfigModule.forRoot` | `config/{env}.yaml` + `Hooks::load_config` | §6.13 |
| `ValidationPipe` | `validator` crate derive + dictionary-driven runtime validation | §6.10 |
| `Logger` | `tracing` (`tracing::info!`) | Loco configures the subscriber |
| `OnModuleDestroy` | `Drop` / explicit shutdown in `Hooks` | e.g. zen-engine cleanup is automatic |

### 6.2 Bootstrap

`src/main.ts.hbs` (225 lines) decomposes into three places:

| Current concern | Becomes |
|---|---|
| Fastify adapter + `listen` | Loco's server — `config/*.yaml` `server.port/binding` |
| `setGlobalPrefix('api', {exclude:['v1/shape']})` | `AppRoutes::with_default_routes().prefix("/api")` for app controllers; Electric registered outside the prefix via `nest_route` |
| CORS allow-list + credentials patch (lines 127–155) | `middlewares.cors` in YAML — the `@fastify/cors` credentials workaround disappears entirely |
| better-auth `/api/auth/*` catch-all mount | Native `controllers::auth` routes — §6.8 |
| `ValidationPipe` | §6.10 |
| `ensureAdminUser()` (lines 16–106) | `cargo loco task ensure_admin` + a `Hooks::seed` path; keep the same env vars (`ADMIN_EMAIL`, `ADMIN_PASSWORD`) |

`src/app.rs` sketch:

```rust
pub struct App;

#[async_trait]
impl Hooks for App {
    fn app_name() -> &'static str { "{{kebabCase project.name}}" }

    async fn boot(mode: StartMode, env: &Environment, cfg: Config) -> Result<BootResult> {
```

### 6.3 ★ The central problem: dynamic, metadata-driven CRUD

**What exists.** `BusService` (800 lines) does everything through `Kysely<any>`:

```ts
const rows = await trx.insertInto(tableName as any)
  .values({ ...processedData, created_at: now, updated_at: now, deleted_at: null } as any)
  .returningAll().execute();
```

`tableName` is computed per request from a URL segment (`getTableName()` — lowercase, singularize, `bus_` prefix). Column set, types, mandatory-ness, and defaults come from `sys_column`/`sys_field` rows read at request time.

**Why the obvious Rust answer fails.** SeaORM entities are compile-time types. Generating one per `bus_*` table does not solve it, because the *controller* is generic: `/api/bus/{entity}` must dispatch to a table named by a runtime string, and validation must follow dictionary rows that an admin can edit **after** the app is compiled.

**Proposed answer: a `DynamicRepo` service** built on `sea_query` (dynamic SQL construction with correct identifier quoting) executing over the sqlx pool SeaORM already owns (`ctx.db.get_postgres_connection_pool()`), returning `serde_json::Value` rows.

```rust
pub struct DynamicRepo { pool: PgPool }

impl DynamicRepo {
    pub async fn find_all(
        &self,
        table: &TableName,          // validated newtype, see below
        opts: &PaginationOptions,
        filters: &[Filter],
    ) -> Result<PaginatedResult<serde_json::Value>> {
        let mut q = Query::select();
        q.expr(Expr::asterisk())
            .from(Alias::new(table.as_str()))
            .and_where(Expr::col(Alias::new("deleted_at")).is_null());

        for f in filters {
            q.and_where(f.to_condition()?);   // operator whitelist: = > >= < <= ILIKE
        }

        let (sql, values) = q
            .order_by(Alias::new(&opts.order_by), opts.order_dir.into())
            .limit(opts.limit).offset(opts.offset)
            .build_sqlx(PostgresQueryBuilder);

        let rows = sqlx::query_with(&sql, values).fetch_all(&self.pool).await?;
        Ok(rows_to_json(rows))          // pg type → serde_json via row.try_get_raw + type oid
    }
}
```

Three non-negotiable safety rules, because table and column names arrive from HTTP:

1. **`TableName` is a validated newtype.** Constructed only via `DictionaryCache::resolve(entity)`, which requires a matching `sys_table` row. An unknown entity is a 404 before any SQL is built. This is stricter than today's `verifyEntity()` and closes the same hole.
2. **Column names are checked against `sys_column`** for the resolved table before entering a query. Anything else is a 400.
3. **Filter operators come from a fixed enum**, never string interpolation. `sea_query` parameterizes values; identifiers go through `Alias`, which quotes.

**Row → JSON conversion** is the fiddly part: Postgres OIDs must map to `serde_json` values so the API keeps emitting exactly what the frontend parses today (numeric → number, `jsonb` → object, `timestamp` → ISO-8601 string, `uuid` → string). This deserves its own module (`src/services/row_json.rs`) and its own unit test per `sys_reference_id` (Appendix A).

**Alternative considered and rejected:** generating a typed SeaORM entity per `bus_*` table plus a generated `match entity { "customer" => …, "order" => … }` dispatcher *as the CRUD path*. It restores compile-time typing but produces O(entities × operations) generated match arms, makes the binary grow with model size, and *still* cannot express dictionary-driven validation edited at runtime. Worth reconsidering only if `DynamicRepo` benchmarks poorly — which is unlikely, since it is the same SQL the current stack sends.

**Typed `bus_*` entities are still coming — for a different job** (D9). Now that `DynamicRepo` has shipped (Phase 3.4), the generator can also emit SeaORM entities per `bus_*` table for use *inside hooks and workflow tasks*, where hand-written Rust benefits from typed field access. They are a convenience layer over the same tables, never the path the generic controller takes.

**Prototype gate:** build `DynamicRepo` + `/api/bus/{entity}` list/get/create against an existing generated database, and run the existing `tests/suites/03-crud.*` suites against it, before committing to the rest of Phase 3.

### 6.4 The `sys_*` Application Dictionary module

The largest single file in the backend (`sys.service.ts.hbs`, 1 071 lines) plus 12 controller/service pairs. These tables **are** fixed-shape, so this module gets the full SeaORM treatment:

- `cargo loco generate model` per `sys_*` table (or hand-written migrations + `cargo loco db entities`), producing `src/models/_entities/sys_table.rs` etc.
- Controllers become thin: `Routes::new().prefix("sys/table")` with `list/get/create/update/delete`, SeaORM `ActiveModel` for writes, `loco_rs` pagination helpers for reads.
- `DictionaryCache` (backed by `moka`) replaces `BusService.metadataCache` / `identifierFieldsCache`. **It must expose explicit invalidation**, wired to every `sys_field`/`sys_column`/`sys_table` write, because the product promise is that reordering a field takes effect without a redeploy.

Estimated 3 500–4 500 lines of Rust; individually simple, collectively the largest slab of work in the backend.

### 6.5 Rules engine — the easy win

```rust
use zen_engine::{DecisionEngine, model::DecisionContent};

pub struct RulesEngine { engine: DecisionEngine }

impl RulesEngine {
    pub async fn evaluate(
        &self,
        jdm: &DecisionContent,
        data: &serde_json::Value,
        operation: &str,           // "create" | "update" | "delete"
    ) -> Result<Vec<RuleEvaluationResult>> {
        let mut input = data.clone();
        // Preserve the existing contract exactly: the CRUD verb travels as
        // `_operation`, never `action`, so a model with an `action` column
        // still fires its own rules. (see rules-engine.service.ts.hbs:110-118)
        input["_operation"] = json!(operation);
        let out = self.engine.create_decision(jdm.clone()).evaluate(input.into()).await?;
        Ok(parse_violations(out))
    }
}
```

Preserved without change: the `_operation` convention, hit-policy `collect` semantics, the `JdmViolation` output shape (`action`, `message`, `ruleId`, `workflowName`, `targetEntity`, `linkField`, `updateData`, `createData`, `transformData`), the "JSON object or JSON string" tolerance in `asObject()`, and the **fail-open** behaviour in `BusService.enforceBusinessRules` — infrastructure failure logs a warning and lets the write through; only a `prevent` action rejects with 400.

Two sources of JDM must both keep working, as today: bundled files under `src/modules/rules/jdm/*.jdm.json` (→ `assets/jdm/` in the Rust layout) and rows stored in the database (`evaluateRulesWithJDM`).

### 6.7 Entity promotion & background jobs

The current design: a row is inserted as a **draft**; `PromotionDispatcher` then runs rules + workflows and decides whether it becomes **final** — via a Trigger.dev task when `TRIGGER_SECRET_KEY`/`TRIGGER_PROJECT_ID` are set, inline otherwise (`promotion-dispatcher.service.ts.hbs:32-45`). The inline path is deliberately a real implementation, not a stub, so a freshly generated app works before anyone signs up for Trigger.dev.

Loco replaces the whole dispatcher concept with configured queue modes:

| `workers.mode` in `config/*.yaml` | Behaviour | Maps to today's |
|---|---|---|
| `ForegroundBlocking` | run inline, in-process | dev/test |
| `BackgroundAsync` | tokio tasks, no external service | **the inline fallback** — new default |
| `BackgroundQueue` | Postgres- or Redis-backed durable queue | the Trigger.dev path, **without a SaaS dependency** |

**Decided and landed (D3): Trigger.dev is dropped entirely.** `workers.mode` is `BackgroundAsync` in development and `BackgroundQueue` (Postgres provider — the app already runs Postgres) in production. This removes a paid external dependency, the `@trigger.dev/sdk` package, `trigger.config.ts.hbs`, and the `TRIGGER_SECRET_KEY` / `TRIGGER_PROJECT_ID` env vars, and gains process separation (`cargo loco start --worker`).

Promotion currently uses `triggerAndPoll` — it **waits** for the result so the POST response carries the final `doc_status`, while a Loco `BackgroundQueue` job is fire-and-forget. **Decided (D3): promotion runs inline, always.** It is a synchronous business decision, not a background job; inline execution preserves the create/update response shape byte-for-byte and matches what the "Trigger.dev not configured" path already does today. Enqueue-and-poll was rejected because it would change the API contract.

`PromotionDispatcher` therefore disappears as a concept — there is no dispatch decision left to make — and `EntityPromotionService` becomes a plain service called from the CRUD path. The queue carries email, report and sync only; those `src/trigger/*.task.ts` files become `src/workers/*.rs` implementing `BackgroundWorker<Args>`.

### 6.8 Authentication — **decided: Loco native JWT** (D1)

**Current:** [Better Auth](https://better-auth.com) — a Node library — mounted as a Fastify catch-all at `/api/auth/*` (`main.ts.hbs:157-193`), with `@better-auth/kysely-adapter`, `sysUserId` linkage into `sys_user`, and a `SessionAuthGuard` reading its session cookie. The frontend imports the matching `better-auth` client (`frontend/src/lib/auth.ts`, `lib/queries/use-auth.ts`).

There is no Rust port of Better Auth. Three paths were considered; **A was accepted and has landed** (Phase 3.3):

| Option | Description | Pros | Cons |
|---|---|---|---|
| **A. Native Loco auth** *(recommended)* | Loco's built-in JWT auth: `users` model implementing `Authenticable`, argon2 hashing, `auth::JWTWithUser<users::Model>` extractor, `auth.secret`/`auth.expiration` in YAML | One language, one process, fully supported, first-class test story | Frontend auth code must be rewritten; session-cookie → bearer-token (or JWT-in-cookie, which Loco supports via `jwt_locations`); social login must be rebuilt if used |
| **B. Better Auth as a Node sidecar** | Keep the Node auth service; Rust validates its session by calling it or sharing the session table | Zero frontend change; keeps social providers | Two runtimes in every generated app — contradicts the point of the migration |
| **C. Rust OIDC/OAuth crate** | `openidconnect` / `oauth2` + custom session store | Full control, social login | Most work; reimplements what Loco already gives you |

**Accepted: A**, with `jwt_locations: cookie` so the frontend's existing "session cookie is set, call `/api/auth/me`" flow survives with minimal change. Schema impact: the Better Auth tables (`user`, `session`, `account`, `verification` — created by `migrations/betterauth.ts.hbs` and `000_create_auth_tables.ts.hbs`) are replaced by a Loco-shaped `users` table. **`sys_user` and the `sys_user_roles` RBAC join stay exactly as they are** — only the credential store changes, and the `sysUserId` link becomes a plain column on `users`.

The roles guard (`roles.guard.ts.hbs`) becomes a middleware layer or a per-handler check against `sys_user_roles`; the `@Roles(...)` decorator becomes a typed extractor or an explicit guard call at the top of the handler.

**Accepted consequences** (§12.2): the frontend auth module is rewritten as part of Phase 2; users are logged out once at cutover; any social-login provider must be reconfigured. `/api/auth/*` is the one deliberate exception to the frozen contract in §9.

### 6.9 The hook system — **decided: generated Rust functions** (D2)

13 lifecycle hook types (`beforeCreate`, `afterCreate`, `beforeUpdate`, …, `beforeList`, `afterList`, `customValidate`) parsed from `hooks` EML directives, translated by `packages/core/src/generators/hook-translator/`, and emitted as TypeScript functions that `BusService` calls (`bus.service.ts.hbs:16`). The shipped template (`hooks.ts.hbs`) is a scaffold — `getHooks()` returns `{}` until workflows are applied.

Rust options:

| Option | How | Trade-off |
|---|---|---|
| **A. Generate Rust hook fns** *(recommended)* | The hook translator emits `src/services/hooks/{entity}/{event}.rs` + a generated registry; `BusService` equivalent calls them | Native speed, compile-time checked, no runtime; **but the translator must learn to emit Rust, and hooks can no longer be edited without recompiling** |
| **B. Embed `rhai`** | Hook bodies stay script, run in an embedded interpreter | Hooks stay editable at runtime (closer to today's feel); new language surface to document; sandbox and perf considerations |
| **C. WASM plugin host** (`wasmtime`) | Hooks compile to WASM from any source language | Maximum flexibility and isolation; by far the most machinery |

**Accepted: A.** The translator gains a Rust emitter alongside its TypeScript one, writing `src/services/hooks/{entity}/{event}.rs` plus a generated registry, built once at boot into `shared_store` (§6.2). Signatures mirror today's semantics: `before*` takes and returns the payload, `after*` takes it by reference, `before_delete` returns `bool`.

**Accepted trade-off** (§12.2): **changing a hook now requires a rebuild** — consistent with the rest of a Rust app, and with hooks being generated *from the model* rather than hand-edited in production. It is still a real change for anyone who edits hook files on a running deployment, and belongs in the release notes. `rhai` stays on the shelf if live editing turns out to be a hard requirement.

Note the ordering guarantee that must be preserved: `before*` hooks run in registration order and **transform** the payload (each receives the previous one's output); `beforeDelete` returning `false` cancels the operation; `after*` hooks are fire-and-forget.

### 6.10 Validation

Three layers today, and all three must survive:

1. **Structural DTO validation** — `class-validator` / Zod on `sys_*` DTOs → Rust `validator` derive macros on typed request structs.
2. **Dictionary-driven validation** — `BusService.validateData(entity, data, mode)` walks `sys_column`/`sys_field` for mandatory-ness, `field_length`, and `sys_reference_id` type coercion. This is **runtime** and must stay runtime: a `DictionaryValidator` service that produces the same 400 body shape.
3. **Business rules** — zen-engine (§6.5).

The `sys_reference_id` → type mapping is the shared vocabulary across all three plus the migration generator; Appendix A gives the full table including the new Rust column.

### 6.11 Error and response envelopes

The frontend parses specific shapes; changing them silently breaks the UI. Two things to preserve exactly:

- **`TransformInterceptor`** wraps successful responses. Reproduce as a small `format::json`-based helper (or a response-mapping layer) rather than a per-handler concern.
- **`HttpExceptionFilter`** (189 lines) shapes errors. Port as:

```rust
pub enum AppError {
    NotFound(String),
    Validation { message: String, errors: Vec<String> },  // 400 — same body as BadRequestException
    Conflict(String),                                     // 409 — ETag / unique violation
    Unauthorized, Forbidden,
    Internal(anyhow::Error),
}
impl IntoResponse for AppError { /* identical JSON shape + status codes */ }
```

Two specific behaviours to carry over verbatim:
- Postgres `23505` (unique violation) → **409** with `"A record with the same unique field value already exists"` (`bus.service.ts.hbs:180-191`).
- Version mismatch on `If-Match` → **409** `"Record was modified by another user. Please reload and try again."`

### 6.12 Optimistic concurrency / ETag

Current: `If-Match: "v3"` → parsed to an integer → compared with `version` inside the transaction → `version + 1` on success (`bus.controller.ts.hbs:274-276`, `bus.service.ts.hbs:242-260`).

Loco ships ETag middleware, but it computes response-body ETags — **not** the same thing as this row-version protocol. Keep the explicit implementation: parse `If-Match` in the handler, compare within the SeaORM/sqlx transaction. Do **not** enable Loco's `etag` middleware on `bus` routes without checking it doesn't collide with the `"v{n}"` format the frontend sends.

### 6.14 Migrations and seeds

`src/migrate.ts.hbs` (173 lines) is a hand-rolled idempotent runner over a `_migrations` table. Loco replaces it with a `migration/` crate and `cargo loco db migrate` — which also means `cargo loco db entities` can regenerate SeaORM entities for the `sys_*` tables from the schema, keeping model code honest.

The seven migration templates port to SeaORM's schema DSL. `002_create_sample_business_tables.ts.hbs` (the `{{#each entities}}` one) is where the `sys_reference_id` → SQL mapping from Appendix A is consumed.

The two seeds (`001_seed_sys_reference`, `002_seed_admin_user`, 415 + N lines) become `Hooks::seed` + a `cargo loco task` — the same idempotent semantics.

⚠ **Emit the identical DDL.** Column names, types, indexes, and the soft-delete/version columns (`id`, `version`, `created_at`, `updated_at`, `deleted_at`, `doc_status`) must match, so a database created by the NestJS generator can be served by the Rust backend. That property makes side-by-side parity testing possible and is worth defending in a test.

**How Phase 1 actually implements this — a deliberate deviation.** The migration crate emits **raw SQL**, not SeaORM's schema DSL, and the static `sys_*` DDL is *extracted verbatim* from the TypeScript migrations into `migration/sql/*.sql` (embedded with `include_str!`). Reasons:

1. Translating to the schema DSL and hoping the emitted SQL matches is a guess re-made on every edit; extraction makes the equivalence structural.
2. Loco 1.0 changed `int` to `i64`/`BIGINT` and `ColType::PkAuto` to `BIGINT`. This schema uses UUID primary keys and a mix of widths chosen by the TypeScript stack. Raw SQL sidesteps the mismatch entirely.
3. `sqlType` and the new `sqlTypeRust` Handlebars helper now share one implementation (`sqlTypeFor` in `loader.ts`), so the two stacks cannot drift apart by editing one map.

The SQL was originally extracted by `scripts/extract-sys-ddl.ts`. With the
NestJS stack removed there is no second schema to stay equivalent to, so the
script has been retired and `migration/sql/*.sql` is now maintained directly —
edit those files.

**Two discrepancies found while doing this**, both worth knowing:

- **Appendix A is wrong about DATETIME.** It lists `sys_reference_id` 16 → `timestamp`. The migration templates the generator actually renders emit `TIMESTAMPTZ`. The Rust migrations follow the templates, not the appendix.
- **The doc pointed at the wrong templates.** §4.2 and Appendix C cite `src/migrations/001_create_sys_tables.ts.hbs` and `002_create_sample_business_tables.ts.hbs`, but `NestJsBackendGenerator.generateMigrations()` renders `common/migrations/sys-tables.migration.ts.hbs` and `common/migrations/bus-tables.migration.ts.hbs` for those two slots. The `src/migrations/00{1,2}_*` files are dead. This matters: the two pairs disagree — the `src/migrations` bus template emits `created_by`/`updated_by`/`deleted_by` and re-emits the primary key as a duplicate column, while the `common/` one guards the PK and omits the `*_by` columns. Phase 1 mirrors the `common/` templates, which are the ones that run.

### 6.15 Audit trail

`audit.interceptor.ts` captures before/after diffs (note the `req.__auditBefore` stash in `bus.controller.ts.hbs:283`) and `immudb.service.ts` mirrors entries into immudb for tamper evidence.

- The interceptor → a `tower::Layer`, or (simpler and more honest) explicit before-value capture inside the handlers that already do it today.
- **immudb has no maintained Rust client, and the mirror is dropped (D4, landed in Phase 4).** `audit_log` in Postgres carries a **hash chain**: each row stores `prev_hash` and `entry_hash = H(prev_hash ‖ canonical_json(entry))`, so a retroactive edit or deletion breaks the chain and is detectable by a verification pass. A `tonic` gRPC client against immudb and an HTTP shim in front of it were both rejected. One external service leaves the generated app's deployment footprint, and the existing audit UI (`routes/admin/audit.tsx`, 702 lines, including its verify affordance) keeps its shape — only the backing check changes.

`src/providers/theme-provider.tsx` — note `LinkProvider`, which is how Astryx components render router-aware links:

```tsx
import { Theme } from "@astryxdesign/core/theme";
import { LinkProvider } from "@astryxdesign/core/Link";
import { neutralTheme } from "@astryxdesign/theme-neutral/built";
import { Link } from "@tanstack/react-router";

export function AstryxProvider({ children }: { children: React.ReactNode }) {
  return (
    <Theme theme={neutralTheme}>
      <LinkProvider component={Link}>{children}</LinkProvider>
    </Theme>
  );
}
```

Mounted in `routes/__root.tsx.hbs`, outside the existing query/electric providers.

**No build plugin, no PostCSS, no Babel config** — Astryx ships pre-built CSS and JS. `@astryxdesign/build` (Vite/Next/Babel/PostCSS plugins) is only needed for a StyleX *source* build, which this project does not need. That single fact removes most of the risk from this track.

### 7.3 The incremental path (why this is safe)

Astryx exports `@astryxdesign/core/tailwind-theme.css`, which maps its tokens onto Tailwind utility names via `@theme inline`:

```css
@layer reset, theme, base, astryx-base, astryx-theme, components, utilities;
@import 'tailwindcss/theme.css'      layer(theme);
@import 'tailwindcss/preflight.css'  layer(base);
@import '@astryxdesign/core/reset.css';
@import '@astryxdesign/core/astryx.css';
@import '@astryxdesign/theme-neutral/theme.css';
@import '@astryxdesign/core/tailwind-theme.css';
@import 'tailwindcss/utilities.css'  layer(utilities);
```

With the bridge in place, `bg-surface`, `text-primary`, `border-border`, `rounded-lg`, `shadow-md` resolve to Astryx tokens. So:

- **Phase A** — add Astryx + bridge; replace `components/ui/*` primitives one at a time. The 2 319 existing `className` sites keep working and start inheriting Astryx's palette automatically.
- **Phase B** — restyle `components/admin/*` and layout onto Astryx layout primitives (`Stack`, `HStack`, `VStack`, `Grid`, `Section`, `Layout`, `AppShell`).
- **Phase C** — drop Tailwind, the bridge import, `cn()`, `clsx`, `tailwind-merge`, `class-variance-authority`, PostCSS, and autoprefixer.

Each phase is independently shippable and independently testable. Phase C can be deferred indefinitely if it stops being worth the churn.

### 7.5 The dictionary-driven form and table

These two files are the heart of the generated UI and deserve explicit design rather than find-and-replace.

### 8.7 Scripts: what `cargo build` + `clap` can absorb

A fair question once the backend is Rust: can the script layer stop being `package.json` entries and become compiled binaries? The answer differs sharply across four families, so they are separated here.

#### (a) Generated backend scripts — **yes, entirely, and mostly for free**

`backend/package.json.hbs` declares 12 scripts. Loco's own CLI is already a clap application, so all of them are absorbed with no bespoke binary:

| Today (`bun run …`) | Loco |
|---|---|
| `start` / `start:dev` / `start:prod` | `cargo loco start` (`--server-and-worker`, `--worker`, `--all`) |
| `build` | `cargo build --release` |
| `migrate` / `migrate:down` | `cargo loco db migrate` / `db down` |
| `seed` | `cargo loco db seed` (via `Hooks::seed`) |
| `db:setup` | `cargo loco db reset` |
| `test` / `test:watch` | `cargo test` / `cargo watch -x test` |
| `lint` / `format` | `cargo clippy` / `cargo fmt` |

Anything project-specific that isn't a Loco subcommand — `ensure_admin`, `seed_dictionary`, a data backfill — becomes a **task** registered in `Hooks::register_tasks` and invoked as `cargo loco task ensure_admin key:value`. Tasks get argument parsing, `--help`, and listing from Loco's clap layer, so no new binary and no new dependency.

If a genuinely standalone binary is wanted (a one-shot importer, an offline dictionary dump), add it to `Cargo.toml` and `cargo build` produces it alongside the server:

```toml
[[bin]]
name = "dictionary-dump"
path = "src/bin/dictionary_dump.rs"
```

```rust
#[derive(clap::Parser)]
#[command(version, about = "Dump the Application Dictionary as JSON")]
struct Args {
    #[arg(long, env = "DATABASE_URL")] database_url: String,
    #[arg(long, default_value = "-")] out: String,
}
```

**Files that disappear from the generated backend:** `package.json`, `bunfig.toml`, `tsconfig.json`, `tsconfig.build.json`, `nest-cli.json`, `knexfile.ts.hbs`, `src/migrate.ts.hbs` (173 lines), `src/seed.ts.hbs`, `run-app.sh`, `trigger.config.ts.hbs`, `biome.json.hbs`, `.eslintrc.cjs.hbs`, `eslint.config.mjs`, `.prettierrc.hbs`. That is **14 files of build/script scaffolding replaced by `Cargo.toml` + `config/*.yaml`** — a real simplification and one of the better arguments for the migration.

#### (b) Generated frontend scripts — **no**

`dev`, `build`, `start`, `test`, `type-check`, `lint` drive Vite, Vitest, `tsc`, and Biome over a React app. Cargo cannot build a React app, and wrapping bun in a Rust binary adds a layer without removing one. These stay as they are.

The generated project therefore ends up **bilingual by design**: `cargo` owns the backend, `bun` owns the frontend. Document this plainly in the generated README so it doesn't read as an oversight.

#### (c) Generated E2E suites — **possible, but deliberately not recommended yet**

`<output>/tests/` (a `run.ts` orchestrator + `bun:test` HTTP suites) could become a Rust integration crate (`cargo test`) or a clap-driven runner using `reqwest`. Two reasons to hold off:

1. These suites are the **cross-stack parity oracle** (§9). Their value comes precisely from being stack-agnostic and running unchanged against both the NestJS and Loco backends. Porting them to Rust destroys that property exactly when it is needed most.
2. `tests/requests/` in the backend crate already gives in-process Rust coverage; the bun suites cover the black-box HTTP contract. They are complements, not duplicates.

Revisit after the NestJS stack is deprecated (D7).

#### (d) This repository's own scripts — **possible via `xtask`, but low value today**

The root `package.json` has 31 scripts and `scripts/` holds 8 shell/TS files. The cargo-idiomatic pattern would be an `xtask` crate — a clap binary invoked as `cargo xtask build`, `cargo xtask e2e`. But nearly every script's body is "invoke bun / biome / playwright / vitest," so the binary would be a wrapper around the tools it claims to replace, and would add a Rust toolchain requirement to a TypeScript monorepo. **Not recommended** unless (e) happens.

#### (e) The bigger question: should the *generator itself* become a clap binary?

`packages/generator/src/cli/generate.ts` is 1 748 lines of Commander with 10 commands. Porting it to Rust + clap is coherent — and Loco itself is evidence the pattern works, since `cargo loco generate` is a clap CLI driving `rrgen` templates. Commander → clap-derive is close to mechanical:

```rust
#[derive(Parser)]
#[command(name = "appwithai", version)]
struct Cli { #[command(subcommand)] command: Command }

#[derive(Subcommand)]
enum Command {
    Generate(GenerateArgs), Inspect(InspectArgs), Validate(ValidateArgs),
    Diff(DiffArgs), Info(InfoArgs), Wizard,
}

#[derive(Args)]
struct GenerateArgs {
    input: PathBuf,
    #[arg(short, long, default_value = "tanstack-astryx-loco")] stack: StackOption,
    #[arg(short, long)] output: Option<PathBuf>,
    #[arg(long)] skip_frontend: bool,
    #[arg(long)] skip_backend: bool,
}
```

What makes it a *project* rather than a port, though, is everything behind the CLI:

| Dependency | Rust story |
|---|---|
| The ERD parser + category parser | Full rewrite; the EML grammar (`language/grammar/appwithai.ebnf`) makes this tractable — `nom`/`pest` — but it is the parser the whole product rests on |
| Handlebars templates (328 files) | `handlebars-rust` renders `.hbs` largely unchanged — **but all ~60 helpers in `loader.ts` (875 lines) must be reimplemented in Rust**, and helper semantics are where subtle bugs hide. `rrgen`/`tera`/`minijinja` are alternatives that would require rewriting the templates |
| `@appwithai/core` types (`Entity`, `BusEntity`, dictionary generators) | Rust structs + a port of `entityToBusEntity` / `generateEntityDictionary` |
| **In-process use by the web app** | `packages/web/src/routes/api/generate.ts` imports the generator directly and streams progress over SSE. A Rust binary turns that into a subprocess boundary needing a JSON/NDJSON progress protocol — the single largest integration change |
| Prettier post-formatting | `cargo fmt` for Rust output; Biome (subprocess) for JS output |

Upside if done: one distributable binary, no Node needed to generate a project, and generation speed that would make the `cargo build` gate (§8.6) the only slow step left.

**Recommendation: do not bundle this into the migration.** Ship the Loco + Astryx stack with the existing TypeScript generator first — the generator's output being Rust does not require the generator to be Rust. Then evaluate the port on its own merits, with a working Rust target already in hand and the parser rewrite as the honest long pole. Recorded as **D11** in §12.

## 9. The API contract (the seam that makes this survivable)

Both tracks depend on the HTTP contract staying still. Freeze it, write it down, and test it — it is what lets the frontend ship against the old backend and the new backend ship against the old frontend.

**Preserve exactly:**

| Aspect | Contract |
|---|---|
| Base path | `/api` (Electric proxy at `/v1/shape`, outside the prefix) |
| Business CRUD | `GET/POST /api/bus/{entity}`, `GET/PUT/PATCH/DELETE /api/bus/{entity}/{id}` |
| Metadata | `GET /api/bus/{entity}/meta`, `/fields/form`, `/fields/grid` |
| Dictionary bootstrap | `POST /api/bus/{entity}/setup-dictionary` |
| Promotion retry | `POST /api/bus/{entity}/{id}/promote` |
| Pagination | `?page=&limit=&orderBy=&orderDir=&search=` |
| Filters | `?filter.{field}={operator}:{value}` with `contains`/`startsWith`/`endsWith`/`equals`/`eq`/`gt`/`gte`/`lt`/`lte` |
| List envelope | `{ data: [...], meta: { total, page, limit, totalPages } }` |
| Concurrency | `If-Match: "v{n}"` → 409 on mismatch |
| Create/update response | row fields **plus** `promotion: { docStatus, message, … }` |
| Soft delete | `DELETE` → **204**, sets `deleted_at` |
| Errors | 400 validation `{ message, errors[] }`, 404, 409, 401/403 |
| Dictionary API | `/api/sys/{table|column|field|tab|window|reference|ref-list|role|user|user-roles|access|val-rule|category}` |
| Rules / workflows | `/api/rules/*`, `/api/workflow/*`, `/api/workflow-definitions/*` |
| Audit | `/api/audit/*` |

**Deliberate exception:** authentication (§6.8). It is the one place the contract must change, which is exactly why it is the first decision to make.

**Recommended artifact:** a contract test suite that runs the *same* assertions against both backends. The generated `<output>/tests/` bun suites already are this — they speak HTTP, know nothing about NestJS, and become the migration's primary oracle at zero additional cost. Protect that property: no stack-specific logic in the suites, only in the harness.

## 12. Decisions — accepted

**All eleven recommendations were accepted on 2026-07-31.** Nothing here is open. The options column is retained as the record of what was considered; the status column records what implementation has since done with each — including the two cases where building the thing changed the answer.

|---|---|---|---|---|
| **D1** | Authentication | **Loco native JWT**, `jwt_locations: cookie`, argon2, `users` implementing `Authenticable`; `sys_user` + `sys_user_roles` RBAC unchanged | Better Auth Node sidecar (two runtimes per app); Rust OIDC crate (rebuilds what Loco gives) | ✅ Landed (Phase 3.3) |

### 12.1 What acceptance removed from the plan

- **Two dependencies leave the generated app entirely**: `@trigger.dev/sdk` and `immudb-node`, along with `TRIGGER_SECRET_KEY` / `TRIGGER_PROJECT_ID` and `trigger.config.ts.hbs`.
- **Three risks retired or downgraded** (§11): R2 (auth) resolved by D1; R5 (immudb) resolved by D4; R4 (formula dialect) eliminated outright by the D6 finding above — a rare case of a risk disappearing because the premise was wrong.
- **R3 stops being a risk and becomes a documented trade**: hooks lose runtime editability by choice (D2).

### 12.2 Consequences to communicate

Two accepted decisions change behaviour a user will notice, and each needs a line in the release notes for the new stack rather than just a commit:

1. **Hooks require a rebuild to change** (D2). Anyone used to editing a hook file on a running deployment must redeploy instead.
2. **Auth tokens replace Better Auth sessions** (D1). Generated apps cannot mix backends across an upgrade; users are logged out once at cutover, and any social-login provider needs reconfiguring.

A third consequence was expected and then withdrawn: `Formula` expressions were going to change dialect (D6), which would have needed a conversion table in the migration guide. The implementation finding means **no model conversion is required** — worth stating explicitly so nobody writes that guide.

### 2026-09-12 — D5 lands; every decision is now closed

The last open decision. `POST /api/ai/query` and an `/ask` page, in both
generators.

**The model does not write SQL, and that is the whole design.** The NestJS
original asked an agent for SQL, validated the string and executed it — putting
generated text on the path to the database with a validator as the only barrier,
which is the class of risk `controllers/electric.rs` deliberately refused to
port. Instead the model returns a `QueryPlan`: an entity, filters drawn from the
operator whitelist `/api/bus/{entity}` already accepts, a sort and a limit.
Every part is checked against the dictionary, and execution goes through
`DynamicRepo::find_all` — the same path the REST endpoint uses. Two consequences
follow and both are the point: a prompt injection has no SQL to inject into, and
the natural-language layer cannot express anything the caller could not already
do over REST. It adds a phrasing, not a privilege.

The cost is real: no joins, no `GROUP BY`, no aggregates beyond the row count
`find_all` already returns. A question needing those gets an honest "closest
entity, and here is what I ran" rather than a query nobody vetted.

**Authorisation is enforced twice on purpose.** The caller's readable tables are
resolved before the prompt is built, so the model is never told about a table
the caller cannot see — the schema itself is not a disclosure. `answer` then
calls `authz::require_read` on the resolved table regardless. The filter is
usability; the check is the control, and it runs even if the model returns
something the filter should have excluded.

**Gated at run time, not by conditional emission.** The route is always mounted
and answers 503 until `ai_base_url` and `ai_model` are set. Skipping the files
instead would repeat the `include_str!` trap this codebase has already been
bitten by, and the parity gate cannot see a file both generators agree to omit.
`config/test.yaml` leaves it unset deliberately, which is what lets the request
suite assert the 503 with no model server present.

**No new crate.** One JSON POST to `/chat/completions` over the `reqwest` that
is already a dependency, rather than an OpenAI SDK — which would have added a
large tree to every generated application, including those that never configure
the add-on, and forced a `Cargo.lock` regeneration.

**Verification.** `cargo clippy --all-targets -- -D warnings` clean on a
generated drug-discovery backend; `bun run parity` byte-identical on all three
corpus models; 552 generator tests and 120 Rust-generator tests pass; five unit
tests in `nl_query.rs` pin the limit clamp, the code-fence unwrap, the
configuration gate, the prompt's table list, and the fact that a plan has
nowhere to put SQL; four request tests cover the guard, the 503, and the request
validation that happens before any model call.

Two things found on the way, neither caused by this change:

1. **The inline-`style={ {…} }` trap is real and I walked into it.** Both new
   `.tsx.hbs` templates died at generation with a Handlebars parse error. The
   styles are hoisted to module scope, and `template-syntax.test.ts` — which
   exists for this — now precompiles all 415 templates green.
2. **Three tests fail on `main`, unrelated to this work.**
   `services::workflow::tests::{divide_by_zero_yields_zero_not_infinity,
   formula_ports_all_four_operations, unknown_operation_passes_the_base_through}`
   assert `Number(0)` against `Number(0.0)` — a `serde_json` integer/float
   comparison in the Formula port. Reproduced on an unmodified checkout before
   attributing it. Left alone rather than folded into this change.

### 2026-09-11 — D9 lands; D2, D7 and D11 were already settled by the work

Picking up "the three pending decisions" turned up that only one of them was
actually pending. The decision table had drifted behind the implementation, so
this entry corrects it and closes the gap.

**D9 — typed `bus_*` entities. Implemented here.** One SeaORM entity per
business table at `src/models/_entities/<table>.rs`, declared by a regenerated
`_entities/mod.rs`, in both generators. They are the convenience layer the
decision described and nothing more: `DynamicRepo` is still the only CRUD path,
because only it can honour a dictionary an admin edits at runtime.

The mapping is the part worth care. It reads a new `seaOrmType` helper rather
than the existing `rustType`, which is wrong for this job in three places — it
yields `DateTime<Utc>` for a `TIMESTAMPTZ` column (SeaORM needs
`DateTimeWithTimeZone`), a bare `NaiveDate` rather than the prelude's `Date`,
and it knows nothing about foreign keys. The foreign-key rule is narrower than
it looks: `m0002_bus_tables` consults `isForeignKey` **only** in the
reference-id 10 and 11 branches, so a `decimal … FK` really is `DECIMAL(18,6)`
in the DDL. Overriding every foreign key to `Uuid` — the obvious
implementation, and the one written first here — produces a struct that
compiles perfectly and fails on the first query. Caught by reading the DDL the
generator actually emits for `bus_order.customer_id` rather than the DDL the
template appears to describe.

`Relation` is deliberately left empty for the same reason: a `DeriveRelation`
arm naming a column that is not a UUID does not compile, and the ERD's
relationships are already enforced by the `FOREIGN KEY` constraints the
migration emits.

**Verification**, because a wrong entity is invisible until runtime:
`cargo check` and `cargo clippy --all-targets -- -D warnings` clean on a
generated drug-discovery backend — 17 entities exercising `Json`, `bool`,
`Date`, `Decimal`, `DateTimeWithTimeZone`, `Uuid` and `i32`; `bun run parity`
byte-identical across all three corpus models, which is what proves the helper
was registered equivalently in both Handlebars engines; two new tests in
`crates/appwithai-gen/src/backend.rs` pin the module/file/`table_name`
agreement and the JSONB and timestamp mappings — the pairing a compile cannot
check.

**D2 — hook execution. Already landed** in PR #24, emitted one file per entity
at `src/hooks/handlers/<entity>.rs` rather than the per-event path §12
predicted. The row is corrected.

**D7 — NestJS stack lifetime. Already done, and more thoroughly than decided.**
The decision was to deprecate after parity with a date set at Phase 5. The
stack was instead removed outright: `StackOption` is the one-member union
`"tanstack-astryx-loco"` and `packages/generator/templates/` holds only
`common/` and `tanstack-astryx-loco/`. No deprecation window was served, so
there is no date left to set and nothing left to remove. Worth noting rather
than quietly ticking off: anyone still generating the NestJS stack lost it
without warning.

**D11 — generator in Rust. Superseded.** `crates/appwithai-gen` is a clap
binary emitting the backend half, held to the TypeScript generator by
`bun run parity`. The deferral held exactly as long as §8.7(e) proposed — until
the stack shipped — but the consequence is now live: **every backend change
lands twice**, in the template *and* in both emission layers, until one
generator wins. This work was itself a worked example: the helper had to be
registered in two Handlebars engines and the emitter written in two languages.

### 2026-07-31 (latest) — decisions D1–D11 formally accepted

The eleven architectural decisions in §12 were **approved by the repository owner**. §12 is retitled and rewritten from a list of open questions into the decision record, and the framing propagated through §3.2, §6.3, §6.6, §6.7, §6.8, §6.9, §6.15, §6.17 and §11 — those sections no longer offer options where a choice has been made.

Phase 4 then found the `Formula` task is a four-way switch over fixed arithmetic with no user-authored syntax at all — so no expression crate is needed, **risk R4 is eliminated rather than accepted**, and the `Formula` conversion table that §12.2 would otherwise have owed the migration guide should not be written. **Five further corrections to this document**, each verified rather than assumed:

1. **`zen_engine::Variable` is not `Send`.** It is built on `Rc<str>` and

   `!Send` and an axum handler will not compile. §2.2 calls the rules module

2. **The `Formula` workflow task is not an expression evaluator.** It reads four
   named properties and switches over four fixed arithmetic operations. There is
   no JavaScript and no user-authored syntax, so **decision D6 is moot and risk
   R4 does not apply** — the port is exact, and no expression crate is needed.
3. **Only seven Astryx themes exist** (D8 above).
4. **`@stylexjs/stylex` is a required runtime dependency.** §7.2's "no build
   plugin, no PostCSS, no Babel config" is true of the StyleX *compiler*, but
   the runtime is a declared peer dependency and 247 files in the shipped
   `dist` import it. Generated apps install it.
5. **The Electric proxy's role clause was an injection vector.** The TypeScript
   original interpolates the attacker-controlled `role` query parameter straight
   into the SQL `WHERE` clause that is the only thing scoping dictionary
   visibility. §6.16 says to keep the clause identical; the Rust port keeps it
   identical for every legitimate role but validates the value first. Tests pin
   the payloads that defeat the original.

separate package with its own build, so UI changes never require recompiling or
restarting the Rust binary, payloads over a LAN are JSON rather than rendered

### 2026-08-01 — Seeds, and three defects the first end-to-end run exposed

The generated `drug-discovery` app (17 entities) was built and run for the first
time through the documented commands. It compiled, migrated, and started — and
then every business route failed. What follows is what that surfaced.

**Shipped**

| Area | What landed |
|---|---|
| Dictionary seed (§6.14) | The generator emits `backend/seed/dictionary.sql` from the model — references, roles, field groups, and per entity a window, table, tab, columns, fields and role access. Every primary key is a UUIDv5 over the object's name, so the file is byte-identical across regenerations and `ON CONFLICT DO NOTHING` makes it idempotent even for the tables (`sys_window`, `sys_tab`, `sys_field_group`, `sys_access`) that have no natural unique key |
| `seed_dictionary` task | `cargo loco task seed_dictionary` — applies the embedded SQL (`include_str!`, so the binary is self-contained) and prints the resulting row counts |
| `ensure_admin` task | `cargo loco task ensure_admin` — creates or refreshes the administrator from `ADMIN_EMAIL` / `ADMIN_PASSWORD`, writing both the `users` credential row (argon2, via `loco_rs::hash`) and the `sys_user` + `sys_user_roles` identity, linked through `users.sys_user_id` |
| `Hooks::seed` | `cargo loco db seed` runs both, dictionary first — `ensure_admin` grants the Administrator role that `seed_dictionary` creates |
| Help text | The ~180 lines of prose-composition logic that lived inside `common/seeds/sys-dictionary.ts.hbs` moved to `generators/dictionary-help.ts`. Both stacks now render the strings that one module returns; the NestJS template inlines them as data |
| `cargo loco` | Generated backends ship `.cargo/config.toml` aliasing `loco` to `run --bin <name>-cli --`, so the command every doc in this repo tells you to run actually exists without a global install |

**Three defects, all found by running the thing**

1. **`services/dictionary.rs` selected `c.ref_table_name` from `sys_column`.**
   That column does not exist — in either stack. It appears in
   `src/migrations/001_create_sys_tables.ts.hbs`, which is never rendered (the
   same stale template that already produced correction 4 above). The NestJS
   `BusService` *derives* the lookup target from the column name; the Rust side
   now does too, via `resolve_ref_table_name`, with the person-role list taken
   from `foreignKeys.personRoleColumns` in `language/appwithai-language.json`
   and a test pinning it against the TypeScript resolver. **Effect before the
   fix: every `/api/bus/*` request returned 500.**

2. **Every `/api/bus/*` and `/api/sys/*` route was unauthenticated.** Anyone
   who could reach the port could read and write all business data and edit the
   Application Dictionary. The NestJS `BusController` carries
   `@UseGuards(SessionAuthGuard)`; the Rust port had no equivalent. All bus
   routes and both audit routes now take a JWT extractor. `sys` reads stay open
   — the frontend builds its navigation from the dictionary before login, which
   is why the NestJS `SysController` has no guard either — but `sys` **writes**
   are authenticated regardless, because a `POST /api/sys/access` can grant a
   role access to any table.

3. **The audit trail was never written.** `AuditService::record` existed, the
   hash chain verified, `/api/audit` and `/api/audit/verify` worked — and
   nothing called `record`. Bus create/update/delete now log, gated on
   `sys_table.is_changelog`, carrying before/after values and the authenticated
   user's `sys_user_id`. Verified end to end: three writes produce three chained
   entries; editing a historical row by hand makes `verify` report
   `verified: false` with the offending id; restoring it re-verifies.

**Gates.** On the generated `drug-discovery` backend: `cargo clippy
--all-targets -- -D warnings` clean, `cargo test --lib` 38 passed. Against a
freshly created database: `cargo loco db migrate` applies all eight migrations,
`cargo loco db seed` reports 17 references / 17 tables / 141 columns / 24
windows / 17 tabs / 141 fields / 2 roles / 41 access rows and creates the
administrator, and the server then answers `/_ping`, rejects unauthenticated
`/api/bus/compound` with 401, serves 17 dictionary tables, and round-trips a
create → list → audit → verify cycle.

**Decisions taken while implementing**

- Dictionary ids are deterministic (UUIDv5, namespaced by project name) rather
  than `gen_random_uuid()`. That is what makes the seed idempotent without a
  natural key to conflict on, and it keeps a saved report or URL that names a
  window id working across regenerations.
- `sys_user.password_hash` is written as `!` — not a real hash and not a copy of
  the argon2 one. It is NOT NULL but is no longer a credential in this stack, and
  `!` parses as no hash format, so nothing can authenticate against it and the
  admin password lives in exactly one place.
- `ADMIN_EMAIL` / `ADMIN_PASSWORD` keep the NestJS defaults (`admin@admin.com` /
  `admin`) because `tests/harness/config.ts` reads those defaults to log in.
  Changing them here would break the cross-stack parity oracle silently.
- `BusEntity.attributes` is narrowed to `BusEntityAttribute[]` in core.
  `entityToBusEntity` already produced them; the type just did not say so.

**A correction to correction 4.** The stale-template trap named in the previous
entry is worse than "differ materially": `src/migrations/001_create_sys_tables.ts.hbs`
declares columns the live schema does not have, and reading it as authoritative
is what produced defect 1. Treat `common/migrations/` as the only source.

mobile-sidebar, scroll-area, slider, table, toast) plus the 18
`components/admin/*`; Phase C (removing Tailwind, `cn()` and CVA) has not
started; hooks (decision D2) are unimplemented; and the shared `tests/` harness
still authenticates through Better Auth's `/api/auth/sign-in/email`, so it
cannot yet drive the Loco stack's JWT login (decision D1's deliberate break).

### 2026-08-01 (later) — Frontend Phase B complete

The seven primitives left over — `dropdown-menu`, `icon`, `mobile-sidebar`,
`scroll-area`, `slider`, `table`, `toast` — are converted, which makes 25 of 25.
Nothing under `src/` imports `@radix-ui/*` any more.

**The four that were not straight renames**

| Adapter | The shape mismatch, and what it cost |
|---|---|
| `toast` | shadcn's `toast()` is module-level and callable from a mutation's `onError`; Astryx's `useToast()` is a hook. A module-level queue bridges them and `<Toaster>` drains it, buffering anything fired before mount — the case that matters is an error during initial load. Astryx has two toast types against shadcn's five variants, so the variant icon is prepended to the body: mapping *success* and *warning* both to `info` would otherwise render "saved" and "check this first" identically |
| `icon` | The dictionary stores arbitrary lucide *names* (`sys_table.icon`), and Astryx's `Icon` accepts a component or one of 26 semantic names — not a free-form name. So lucide resolves and Astryx renders: theme-driven colour and size, with any dictionary-supplied name still working. This is why `lucide-react` stays a dependency and Radix does not |
| `scroll-area` | No Astryx counterpart, deliberately — `scrollbar-width` / `scrollbar-color` became styleable everywhere the generated app runs, so Radix's draw-your-own-scrollbar approach has nothing left to fix. Implemented on the native scroller, which also restores the OS "always show scrollbars" setting that a drawn bar cannot honour |
| `table` | Astryx ships a data-driven `Table` *and* the parts it is built from. The parts are what map onto the shadcn composition; routing the admin grids through the data-driven component would have meant rewriting every call site that interleaves its own cells and row actions |

**Dead dependencies removed.** With every primitive converted, the generated
`package.json` drops 12 `@radix-ui/*` packages plus
`class-variance-authority` — 15 in total, all previously installed and bundled
by every generated app for nothing.

**Prop surfaces widened.** Typechecking the generated frontend surfaced ~50
errors from adapters written in the earlier pass whose props were narrower than
their call sites: pass-through parts typed `{ children?: ReactNode }` while
`components/admin/*` passed `className`, `Input` missing `autoComplete` /
`maxLength` / `step` / `autoFocus`, `SelectItem` missing `disabled`,
`TableRow`'s `data-state` typed `string` where call sites write
`isSelected && "selected"`. An adapter its call sites cannot typecheck against
is not a finished adapter, so all of them are now declared. Two props
(`colSpan` on a header cell, `autoComplete`/`maxLength` on a text input) are
absent from Astryx's types but do reach the DOM through its rest spread; those
are bridged in one commented helper each rather than with a cast per call site.

**Two bugs worth recording**

1. **Handlebars eats JSX style props.** An inline `style={ {…} }` puts two
   braces in the template and generation dies with a parse error — the same
   trap as the Rust `{{` escaping in §14's first entry. Fixed by hoisting every
   style object to module scope, which is where constants belong anyway, so the
   templates are structurally incapable of hitting it again.
2. **`biome.json` was invalid in every generated frontend.** The template put
   `organizeImports` inside `javascript.formatter`, which Biome 1.9 rejects
   outright — so `bun run lint` failed with a configuration error in every
   generated project of *both* stacks, and had been doing so unnoticed because
   the generator only reports "linting found issues". Moved to the top level.

**Gates.** On the generated frontend: `tsc --noEmit` reports no errors in
`components/ui` or in anything importing it, and `biome check src/components/ui`
is clean across all 25 files. The 80 residual project-wide errors are the
pre-existing set — `routeTree.gen` is produced by the router plugin at build
time, not by generation, and every `"/route" is not assignable to never` follows
from its absence.

**Phase C is what remains**: `components/admin/*` still composes through the
Tailwind bridge and `cn()`. Moving those call sites onto Astryx's own API — and
deleting the bridge, `cn()`, and the Tailwind toolchain with them — is the last
step, and the adapters are what make it possible to do screen by screen.

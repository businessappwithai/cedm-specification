Chapter 04

Generate the application

Two ways in: the CLI, which is what you will use once you trust the model, and the browser designer, which is better the first time because it renders the ERD, validates as you type and keeps versions. Both call the same pipeline, so both produce the same application.

Path A — the command line

  1. Check the model

    Optional, because the generator runs the checker itself, but it is instant and it tells you the truth before anything is written.

    shell
    bun language/cli/eml.ts validate -i language/yaml/examples/crm.eml.yaml
# 0 errors, 0 warning(s)

  2. Generate

    One command, from the root of cedm-specification. --no-setup keeps it from installing and migrating straight away, which you want the first time so you can look at what it produced.

    shell
    bun run generate:tanstack -- \
  --input language/yaml/examples/crm.eml.yaml \
  --output generated-projects/crm \
  --name crm \
  --force --no-setup

    It prints what it found as it goes: entities and their attribute counts, then the rules, hooks, sagas, state machines and categories it compiled. Read that list — it is the fastest way to notice a part of the model that did not compile the way you meant.

  3. Point it at a database

    shell
    cd generated-projects/crm
cp backend/.env.example backend/.env
createdb crm_development
# backend/.env, if the database is not local:
# DATABASE_URL=postgres://postgres:postgres@127.0.0.1:5432/crm_development

    The database is <crate>_development, the default baked into backend/config/development.yaml; DATABASE_URL overrides it everywhere. The URL is the one line worth checking by hand.

  4. Install, migrate, seed

    shell
    cd backend
cargo loco db migrate   # the sys_ dictionary, the bus_ tables, the indexes
cargo loco db seed      # every seed task, in order

    The seeds run in a deliberate order: the dictionary (tables, columns, windows, tabs, fields, your model's enums and categories), then the workflow definitions a saga names, then the access rules a transition names, then the administrator. Rules, reports and sample business data are seeded from the model the same way. Every seed is idempotent, so running it twice changes nothing.

  5. Run it

    shell
    cargo loco start --server-and-worker   # backend :3000
cd ../frontend && bun install && bun run dev   # frontend :3001

    Sign in with the admin user the backend creates on first start — ADMIN_EMAIL and ADMIN_PASSWORD in backend/.env, admin@admin.com / admin by default. docker compose up at the project root does all of this in containers instead.

Useful flags

--dry-run lists the files it would write without writing them. --db neon targets a Neon database instead of a local PostgreSQL. --skip-frontend / --skip-backend generate one half. --skip-cli-scaffold generates without running loco new, for offline builds. --run-tests-fast runs the generated suite afterwards, skipping the bulk-seed volume tests, whose size --records-per-entity sets.

Path B — the browser

The generator ships as an application in its own right. Run bun run dev at the repository root and open localhost:3000. It walks a project through six steps: define, discover, logic, generate, enhance, deploy.

Validate reads the drawing into the model and runs the checker over it, reporting the entity count when it reads, and the error with a line number and caret when it does not.

Which path should you use?

Use the browser while the shape of the model is still moving: the live ERD catches a wrong cardinality faster than reading cardinalities, and Versions gives you a way back. Use the CLI once the model lives in version control, because it is scriptable, it is what CI runs, and it produces the same output.

Regenerating safely

You will regenerate constantly — the model changes, the application follows. The rules about what survives are simple and worth knowing before you start editing generated code.

WhatOn regeneration
src/hooks/handlers/<entity>.rsKept. Written once; new hooks are appended. Your logic is safe.
src/hooks/mod.rsRewritten — it is pure wiring.
Workflows and rules marked from the modelRewritten. The model owns them.
Workflows built in the app's own designerKept. They carry source: designer and regeneration never touches them.
Dictionary help you editedKept. The dictionary seed inserts only the rows that are not there yet, so it never overwrites an edit.
Everything else under backend/src/ and frontend/src/Rewritten. Treat it as build output.
Restart after regenerating

Regenerating replaces the front-end source underneath a running dev server, which usually kills it. Stop the app, regenerate, run cargo loco db migrate && cargo loco db seed in backend/ if the model's schema, enums, rules or workflows changed, then start it again.

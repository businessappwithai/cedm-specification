Chapter 03

Workflows

Rules decide. Workflows do. A model has three kinds, and picking the right one is most of the work: a state machine for the lifecycle an object moves through, a hook workflow for side effects around a single write, and a saga for a process that touches several entities and carries values between steps.

KindWritten underReach for it when
State machinestateMachinesA record has a status with legal transitions and roles allowed to make them.
Hookshooks (and, to draw them, hookFlows)Something must happen around a write to one entity: normalize, validate, notify, block.
SagasagasOne event should create or change records across several entities, in order.

State machines

Each state is a value of the entity's status column; each transition is a change the application will allow. Everything else is refused.

emlexamples/crm.eml.yaml · Section 10, with its access rules and triggers
stateMachines:
  - name: LeadLifecycle
    title: Lead Lifecycle
    entity: Lead
    states: [new, working, nurturing, qualified, converted, disqualified]
    initial: new
    final: [converted, disqualified]
    transitions:
      - { from: new,       to: working,      trigger: engage }
      - { from: working,   to: nurturing,    trigger: nurture }
      - { from: nurturing, to: working,      trigger: re_engage }
      - { from: working,   to: qualified,    trigger: qualify }
      - { from: qualified, to: working,      trigger: return_to_working }
      - { from: qualified, to: converted,    trigger: convert }
      - { from: working,   to: disqualified, trigger: disqualify }
      - { from: nurturing, to: disqualified, trigger: disqualify }
      - { from: new,       to: disqualified, trigger: reject }

rbac:
  - { entity: Lead, action: update,     roles: [sales_rep, account_executive, sales_manager] }
  - { entity: Lead, action: convert,    roles: [sales_manager, sales_ops] }
  - { entity: Lead, action: disqualify, roles: [sales_manager] }

triggers:
  - { entity: Lead, source: "webhook:marketing", handler: ingestInboundLead }
  - { entity: Lead, source: "cron:0 7 * * 1",    handler: recycleStaleLeads }
Three rules the checker enforces

There must be an initial state; every state must be reachable from it; every state must have a path to one of the final states. A state you can enter and never leave is almost always a modelling slip, and it is invisible until a record is stuck in it.

An rbac entry whose action names a transition's trigger restricts that transition to roles. A triggers entry declares what else can start one: cron:, webhook: or message:. A source is quoted, because a cron expression holds spaces and *.

What the generator does with it

Each state machine becomes a workflow definition holding BPMN. On create the definition puts the new record into the machine's initial state — new, written to the entity's status column. On update it records a run without touching the state: the transitions constrain what an update may do, they are not a licence to rewind it. The full machine is stored in the definition's description, which is what the Workflow Designer displays.

Hooks

Each entry under hooks binds a named handler to one lifecycle event on one entity, and may name the columns it concerns. Those entries are what the generator compiles. A hookFlows entry is the same process as a drawing — the request, the hooks in the order they fire, the response — for the reader and the viewer; it compiles to nothing on its own.

emlexamples/crm.eml.yaml · the Contact hooks (Section 16 draws them)
hooks:
  - { entity: Contact, event: beforeCreate,   handler: normalizeEmail,            fields: [email] }
  - { entity: Contact, event: customValidate, handler: ensureUniqueEmail,         fields: [email] }
  - { entity: Contact, event: afterCreate,    handler: enqueueWelcomeSequence }
  - { entity: Contact, event: afterUpdate,    handler: syncToMarketingPlatform,   fields: [email_opt_out] }
  - { entity: Contact, event: beforeRead,     handler: enforceFieldLevelSecurity }
  - { entity: Contact, event: afterRead,      handler: maskPersonalData,          fields: [phone, mobile] }
  - { entity: Contact, event: afterDelete,    handler: purgeMarketingConsent }

The thirteen events

PhaseHooksSignature
CreatebeforeCreate, afterCreate before* receives the payload and returns it, changed or not.
after* receives the record and returns nothing.
beforeDelete receives the id; return false to block.
customValidate receives the record; throw to reject.
UpdatebeforeUpdate, afterUpdate
DeletebeforeDelete, afterDelete
ReadbeforeRead, afterRead, beforeList, afterList, beforeQuery, afterQuery
AnycustomValidate
Hooks are where your code goes

Each entry generates a handler function in backend/src/hooks/handlers/<entity>.rs. That file is written once and never overwritten — the bodies are your application logic. Adding a hook to the model later appends a new function; the registry that wires them up (src/hooks/mod.rs) is rewritten every time. So: declare the hook in the model, write the body in the generated project, regenerate freely.

This is also the honest answer to "where does the code I still have to write live?". A minted account number, a welcome email, a masked phone number: the model says that it happens and when; you say how.

Sagas: multi-step processes

A saga is a list of executable steps, run in the order they are written. Each step has an id, a type, a label the application displays, and the properties its type needs. This is how one event reaches several tables.

emlexamples/crm.eml.yaml · Section 22 — lead conversion
sagas:
  - name: LeadConversion
    title: Lead Conversion
    entity: Lead
    trigger: rule
    steps:
      - id: B
        type: Decision
        label: Size the account
        properties:
          decisionTable: '{"hitPolicy":"first","inputs":[{"id":"i1","name":"Score","field":"score"}],"outputs":[…],"rules":[…]}'
      - id: C
        type: CreateEntity
        label: Open the account
        properties:
          entity: Account
          as: newAccountId
          fields: '{"name":"company_name","tier":"accountTier",…}'
      - id: D
        type: CreateEntity
        label: Create the primary contact
        properties:
          entity: Contact
          as: newContactId
          fields: '{"account_id":"newAccountId",…}'
      - id: E
        type: CreateEntity
        label: Open the first opportunity
        properties:
          entity: Opportunity
          as: newOpportunityId
          fields: '{"account_id":"newAccountId","contact_id":"newContactId",…}'
      - id: F
        type: UpdateEntity
        label: Mark the lead converted
        properties: { field: status, value: converted }
      - id: G
        type: UpdateEntity
        label: Stamp the account tier
        properties: { entity: Account, targetSource: newAccountId, field: tier, source: accountTier }

Steps share a context

This is the mechanism that makes a saga more than a list of writes. Every step can read the triggering record's columns plus anything an earlier step published:

  • CreateEntity publishes the new row's id under as.
  • Formula publishes its result under target.
  • Decision publishes one variable per output column of the row that matched.
  • A later step reads one by naming it in source or targetSource.

In the saga above, step B decides the tier, step C creates the account and binds its id as newAccountId, step D wires the contact to that exact account, and step G reaches back into the row step C created. Without the shared context a workflow could insert a row and never touch it again.

The step types

TypeRequiredDoes
Decisionone of decisionTable / ruleEvaluates a table and publishes its outputs. rule names a rule declared elsewhere instead of forking a copy of it.
CreateEntityentity, fieldsInserts a row, publishing its id under as.
UpdateEntityfield + one of source/valueWrites one column, on the triggering record by default.
DeleteEntity—Soft-deletes by default; hard: true removes the row.
Formulatarget, operationmultiply, divide, add, subtract, set, copy.
RESTurlCalls an external endpoint; bodyTemplate interpolates context values.
Two traps worth naming

Row targeting. To touch another entity you must say which row: either targetSource (a context key holding an id) or targetField (a foreign key matched against the triggering row). Naming an entity with neither is refused rather than guessed — updating the wrong row is bad, deleting it is worse.

JSON in a property. fields and decisionTable are JSON held in a YAML string. Quote the whole value with single quotes, so the double quotes inside it stay JSON's; the checker reports a value that does not parse rather than letting a step run with half its fields.

Two ways a saga starts

eml
  - name: LeadConversion
    entity: Lead
    trigger: rule              # runs when a rule's trigger-workflow action names it
  - name: ClosedWonHandoff
    entity: Opportunity
    operation: UPDATE          # trigger: automatic is the default

trigger: rule runs only when a rule's trigger-workflow action names it, so the rule's condition decides. trigger: automatic runs on every write matching operation. Choose rule whenever the process should not fire on every save — an automatic workflow "gated" on a condition would run regardless of it.

The workflows in the CRM

Open one

A list of definitions proves the model was read. Opening one proves it was understood. This is LeadConversion — the saga written out earlier in this chapter — as the running application renders it.

This is an editor, not a viewer

Add another rule, New rule and the step list are live. A definition marked from the model is owned by regeneration, so treat the model as the source of truth for anything you want to keep — but an operator can inspect, disable or extend a process without waiting for a release.
